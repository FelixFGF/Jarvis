# Jarvis Computer Use: capture, coordinates, and safety

## Approval and session lifecycle

The first Computer Use call requests one-time permission. It does not capture the screen or send input before approval. After approval, the request-scoped session starts and the click-through overlay appears. Denial, cancellation, completion, failure, and window closing clear session authorization, pending screenshots, coordinate maps, pause state, and the overlay. Consequential actions still require their own approval.

## Desktop discovery

`inspect_desktop` reports Windows Forms monitor device names, physical bounds and work areas (including negative origins), primary status, DPI and scale, orientation, the virtual desktop rectangle, visible titled windows, process IDs/names, window bounds and minimized/maximized state, foreground window, and the window-to-monitor association based on the largest intersection. A fullscreen flag is explicitly a heuristic: the window must cover the full monitor bounds; exclusive fullscreen cannot be identified reliably for every application. Foreground UI Automation controls are included when Windows exposes them. The taskbar is not inferred to be visible because it can be auto-hidden or covered.

Monitor names are Windows device identifiers and are stable for the current display arrangement, but can change after hardware/driver configuration changes. Each per-monitor screenshot is separate. The overview attaches it with the monitor ID, capture time, source bounds, image size, and independent pixel-to-physical-coordinate scaling. A combined virtual-desktop image remains available through `computer_observe_screen`; it carries the virtual desktop's negative-or-positive origin and exact image dimensions.

## Capture and coordinate mapping

`WindowsComputerUseService.CaptureScreen` captures `SystemInformation.VirtualScreen`; `CaptureMonitor` captures one requested `Screen.DeviceName`. Both use `Graphics.CopyFromScreen`, preserve aspect ratio, resize so the largest image dimension is at most 1600 pixels, encode JPEG, and retain local transient metadata containing the source rectangle, encoded image dimensions, and UTC capture time. `App` calls `System.Windows.Forms.Application.SetHighDpiMode(PerMonitorV2)` in its static constructor before WPF startup creates windows, with the same mode declared to the SDK analyzer. This makes `SystemInformation`, `CopyFromScreen`, `SetCursorPos`, `GetCursorPos`, and window geometry use the same physical virtual-desktop coordinate space on mixed-DPI displays. Screenshots are sent only after the user accepts the Computer Use permission, to the configured model endpoint.

`ScreenshotCoordinateMap` maps image pixel centers to physical desktop coordinates and maps target rectangles with conservative floor/ceiling bounds. Per-monitor captures use that monitor's physical screen rectangle, while combined captures use the virtual desktop rectangle. A visual click must now provide the exact `observation_id`, screenshot-pixel point, screenshot-pixel target rectangle, confidence, and—when using a per-monitor image—the exact `monitor_id`. Jarvis rejects stale/missing observation IDs, low-confidence or out-of-image targets, points outside their boxes, and boxes outside the observed foreground window. No guessed scaling factor or offset is applied. Resized captures map using their recorded output dimensions and original physical bounds; a crop must be represented by its own physical source rectangle. DPI values are descriptive metadata, not another multiplier on already-physical bounds. Before input, Jarvis also checks observation freshness, foreground HWND/bounds and that the selected display geometry still matches the captured mapping.

## Firefox private window

`open_private_browser` currently supports Firefox. Jarvis locates an installed/running Firefox executable or a registered App Paths entry, validates that an optional destination is HTTP(S), then starts Firefox with separate process arguments using Mozilla's documented `-private-window [URL]` option ([Firefox command-line parameters](https://firefox-source-docs.mozilla.org/browser/CommandLineParameters.html)). It does not close existing windows or use a shell command. The tool confirms that a visible Firefox window exists, but deliberately returns `private_window_verified=false`: the agent must use `inspect_desktop` and visible evidence to verify both the private indicator and destination before claiming completion. Actual Firefox behavior depends on the installed version/profile and must be verified on the target PC.

## Input and verification

Mouse and keyboard events use `SetCursorPos` and `SendInput`; keyboard shortcuts are allow-listed and system/security chords are rejected. For visual clicks, Jarvis maps the model-proposed target box and point, moves the cursor, reads the actual position with `GetCursorPos`, checks that it remains within a target-size-derived tolerance and inside the intended bounds, then reads it again immediately before dispatch. A failed position check prevents the click. The action result includes the screenshot ID, mapped target, intended desktop point, measured position and positioning verification; this is execution evidence, not semantic proof that the UI action worked. Jarvis then captures and attaches a fresh observation. An accepted input remains unverified until the agent inspects the next state and updates the task plan from evidence. Windows UI Automation is used to enumerate accessible foreground controls and invoke exact uniquely identified controls when supported; visual input remains the fallback for inaccessible controls.

The chat tool loop treats each model response as one decision snapshot. After any desktop observation or action (including `inspect_desktop`), it executes no later calls from that same response; skipped calls receive explicit tool errors, and the new observation is returned on the next inference turn. Input actions receive an action ID linked to the request, active plan step, source observation, target and intended plan result. The post-action screenshot receives a distinct observation ID. Before another input action can run, Jarvis requires `computer_verify_outcome` or a matching `plan_update` that references those exact IDs. The executor checks that the observation is newer than the source, still fresh, and belongs to the unchanged foreground window; stale IDs, overlapping actions and late results cannot complete a plan step. A matching verification updates the linked checklist; an observed unsuccessful attempt remains recoverable, while uncertain evidence remains explicitly unresolved.

The executor authoritatively validates action dispatch and observation provenance. Semantic interpretation of pixels (for example, whether Discord's screen-share indicator is still active) is still performed by the configured vision-capable model unless an exposed Windows UI Automation state gives a direct machine-readable answer. The model's verification claim is therefore grounded to one exact fresh image and cannot be detached from the action, but this is not an independent semantic vision classifier. If the configured model cannot reliably interpret that image, Jarvis must report uncertainty rather than mark completion.

## Inference provider and recovery

Every Computer Use inference request uses the endpoint and model selected for that request. The default path remains the configured provider (including an OpenAI-compatible local endpoint such as Ollama); screen and monitor capture continue to use Windows APIs and do not depend on the text provider. Temporary HTTP 429 rate limits receive at most three retries, using `Retry-After` when supplied and otherwise bounded exponential delays. Responses indicating exhausted quota are never automatically retried.

In Settings → AI Connection, users may configure a separate OpenAI-compatible Computer Use fallback endpoint and model. A DPAPI-protected optional key is kept separately from the primary provider key. The user must affirm that the fallback model supports image input and tool calls because OpenAI-compatible endpoints do not expose dependable capability metadata. When the selected provider reports exhausted quota or exhausts temporary 429 retries, Jarvis retains the current conversation/tool history, captures a fresh screen, and switches subsequent inference steps to the fallback client. The fallback gets its own HTTP client and authorization header; it never inherits the primary provider's key. If no compatible fallback is configured, the current task pauses with an in-chat Retry action. A retry first captures a new screen and does not replay prior tool actions. Provider errors are reported without echoing response bodies or credentials.

Capability support is checked against actual provider responses where possible. This configuration is an explicit user attestation, not a guarantee from model metadata; an endpoint may still reject image or tool payloads, in which case Jarvis reports that limitation and preserves the prior task context. The automated transport test uses a mocked Ollama-compatible endpoint; it does not verify a live Ollama model or real cloud quota behavior.

## Overlay and limitations

The overlay is scoped to the actual foreground/selected monitor, is click-through and does not activate itself. When using a per-monitor screenshot to click/scroll, it moves to that monitor. It is removed on stop, cancellation, completion or failure. Multi-monitor discovery and mapping have unit coverage for negative origins, mixed DPI values, portrait geometry, and off-screen windows. These tests use simulated geometries; physical mixed-DPI and multiple-monitor interaction must still be verified on the user's specific hardware. The sensitive-screen check is based on foreground title heuristics and cannot detect all private content.
